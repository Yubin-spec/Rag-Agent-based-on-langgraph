# 智能体评估指标体系（可落地字段 + 离线可复现口径）

面试官常问的“评估指标有哪些”，通常指三类问题：

1. 我们怎么衡量“效果好不好”（正确性/相关性/是否有依据）
2. 我们怎么衡量“系统稳定不稳定”（是否失败、是否兜底、是否需要重试）
3. 我们怎么衡量“性能与成本”（延迟、缓存命中、重检/重生成次数等）

本文按“线上可观测指标（已落地）+ 离线可复现评估指标（已在代码中提供）+ 评估闭环流程（如何用这些指标改进）”来整理。

---

## 1. 指标口径总览（你可以把它当作回答框架）

### 1.1 效果类（Effect）

- 目标答案是否可接受（通过 `success`、`quality_label`、`final_status` 与兜底原因来聚合）
- 生成是否与证据对齐（通过 `grounding_score`、`has_evidence_citations`、`rag_answer_grounding_min_score` 门控）
- 检索是否足够相关（通过 `top_match_score`、`top_normalized_score`、`source_count`、`retrieve_attempt`，以及离线 `evaluate_retrieval()` 指标）

### 1.2 可靠性类（Reliability）

- 是否失败或超时（通过 `success=false`、`route=timeout/cancelled/...`）
- 是否触发降级/兜底（通过 `quality_label` 与 `fallback_reason`）
- 是否需要多轮修正（通过 `regenerate_count`、`second_round_used`、`retrieve_attempt`）

### 1.3 性能与成本类（Performance & Cost Proxy）

- 端到端延迟（通过 `latency_ms`）
- 低成本路径比例（缓存命中 `used_cache`、高频 QA 命中 `qa_hit` 等）
- “为了达标付出了多少调用/重检/重生成”（通过 `retrieve_attempt`、`regenerate_count`）

### 1.4 可观测与复盘类（Observability）

- 能否快速定位：需要 `observation_id` 串起“路由 -> trace -> 差评案例”
- 能否可复现：离线评估指标要能在不调用模型的情况下复算（本项目检索评估 `src/kb/retrieval_eval.py` 属于此类）

---

## 2. 线上/运行时评估指标（已落地，可由 `/qa/analytics` 聚合）

线上指标主要来自两张表：

1. `qa_observation`（请求级观测）
2. `qa_rag_trace`（RAG/检索生成过程追踪，部分 route（如 `qa_hit`、`text2sql_*`）也会带相关 trace 字段）

接口侧入口是：

- `GET /qa/analytics?days=7&limit=20`：总览统计 + 差评案例 + 反馈标签统计 + 场景统计

### 2.1 基础效果与稳定性指标（来自 `qa_monitoring.get_summary`）

以下字段的计算来自 `src/qa_monitoring.py` 的 `get_summary()`：

- `total_questions`：样本总数
- `success_count`：`qa_observation.success=true` 的请求数
- `cache_hit_count`：`qa_observation.used_cache=true` 的请求数
- `knowledge_count`：`route in ('knowledge','qa','text2sql','rag','cache')` 的请求数
- `negative_feedback_count`：用户反馈 `rating='down'` 的数量
- `positive_feedback_count`：用户反馈 `rating='up'` 的数量
- `avg_latency_ms`：`qa_observation.latency_ms` 的均值
- `low_grounding_count`：`qa_rag_trace.grounding_score` 在 `(0, 0.18)` 区间的请求数
- `regenerated_count`：`qa_rag_trace.regenerate_count > 0` 的请求数
- `fallback_count`：`quality_label in ('fallback','low_grounding','needs_human','no_retrieval_hit')` 的请求数

把它们用一句话串起来就是：

- 成功率看 `success_count/total_questions`
- 质量与兜底看 `fallback_count`、`low_grounding_count`、`regenerated_count`
- 性能看 `avg_latency_ms`
- 成本代理看 `cache_hit_count`

### 2.2 请求级明细指标（用于“定位问题在哪一段”）

每条请求会有一个主键：

- `observation_id`：一次问答的请求级 ID，在前端/反馈/分析接口里用它串起来

请求级字段（`qa_observation`）：

- `route`：路由到哪类链路（`chat/knowledge` 等上层语义；更细的判别会落到 trace）
- `response_mode`：`sync` 或 `stream`
- `success`：是否成功生成可用回复
- `used_cache`：是否命中 Redis/缓存快路径
- `pending_sql`：是否生成了待人工确认 SQL（删除/修改类场景）
- `latency_ms`：端到端延迟
- `quality_label`：用于聚合统计的质量标签
- `fallback_reason`：兜底原因
- `llm_model`、`llm_endpoint_name`：命中的 DeepSeek 节点信息（用于按 LLM 节点分桶排障）

`quality_label` 的生成逻辑在 `api/main.py`：

- 当 `success=false`：返回 `failed`
- 当 `route=chat`：返回 `chat_response`
- 当 `route=cache`：返回 `cache_hit`
- 当 `trace.final_status in ('qa_hit','text2sql_answer','text2sql_pending','rag_grounded','rag_regenerated')`：直接映射为该 `final_status`
- 当 `final_status in ('rag_no_hit','rag_no_context')`：返回 `no_retrieval_hit`
- 当 `final_status='rag_fallback_unconfirmed'`：返回 `fallback`
- 否则若 `fallback_reason` 存在：返回 `fallback_reason` 前 64 字符

RAG 过程追踪字段（`qa_rag_trace`）：

- `final_status`：RAG 结果状态（例如 `rag_grounded`、`rag_regenerated`、`rag_no_hit`、`rag_no_context`、`rag_fallback_unconfirmed` 等）
- `retrieve_attempt`：检索通过的尝试次数（最多由 `rag_max_retrieve_attempts` 控制）
- `top_match_score`、`top_normalized_score`：最佳候选的匹配与综合得分（来自离线 `evaluate_retrieval`）
- `grounding_score`：最终答案与检索证据的最大关联度（生成对齐分数）
- `regenerate_count`：答案重生成次数（最多由 `rag_answer_max_regenerate_times` 控制）
- `has_evidence_citations`：答案是否显式带证据编号（`[证据N]`）
- `source_count`：命中的切片数量
- `scenario_templates`：本次命中/选择的场景模板（用于分析触发的业务模板分布）
- `retrieved_doc_ids`、`retrieved_chunk_ids`：命中的来源 ID 与切片 ID
- `extra`：可包含二次 RAG 等扩展信息（以 trace dict 的结构为准）

### 2.3 差评案例与反馈标签指标（用于“找对问题类别”）

`GET /qa/analytics` 会返回：

- `bad_cases`：差评/低 grounding/兜底优先的案例列表（可直接用于复盘）
- `feedback_tags`：统计用户反馈中的标签分布（`qa_feedback.tags`）
- `scenarios`：统计 trace 命中的场景模板分布（`scenario_templates`）

差评筛选规则在 `src/qa_monitoring.py:list_bad_cases()`，优先条件包括：

- 用户 `rating='down'`
- `grounding_score < 0.18`
- `quality_label in ('fallback','low_grounding','needs_human','no_retrieval_hit')`

## 3. 离线/可复现评估指标（RAG 检索评估与门控）

本项目强调：检索评估计算不依赖模型或大模型调用。

- `src/kb/retrieval_eval.py`：对文本进行纯文本/规则评估，输出一组在 `[0,1]` 范围内的指标

### 3.1 检索文本评估指标（`evaluate_retrieval()`）

对单条候选文本（或候选 chunk 拼接后的文本）计算：

- `match_score`：综合匹配度，范围 `[0,1]`
  - 覆盖率 `query_coverage` 权重 `0.5`
  - 命中密度 `density` 权重 `0.5`
- `irrelevant_ratio`：无关信息比例，范围 `[0,1]`
  - 直观含义：候选文本中“没有被 query 覆盖”的部分占比
- `query_coverage`：问题词在文本中的覆盖率，范围 `[0,1]`
  - 实现口径：把 query 的“字符 + 相邻 2 字符滑窗 terms”当作术语集合，判断这些 terms 是否出现在候选归一化文本中
- `normalized_score`：归一化综合得分
  - 计算：`normalized_score = match_score * (1 - 0.5 * irrelevant_ratio)`

实现细节（面试时可以说“我们有可解释的离线口径”）：

- 命中位置用字符级搜索与合并区间
- 覆盖率与密度通过命中长度与总归一化长度计算

相关函数：

- `evaluate_retrieval(query, text)`
- `compute_match_score() / compute_query_coverage() / compute_irrelevant_ratio()`

### 3.2 RAG 检索通过/重检指标（`RAGRetriever.retrieve_with_validation()`）

检索通过的判定依据来自配置与离线评估：

- `min_score`：最小匹配阈值（来自 `rag_min_match_score`）
- 允许的无关比例上限（实现中用于 `_is_retrieval_acceptable()`）

过程指标：

- `retrieve_attempt`：重检通过所需尝试次数（最多 `rag_max_retrieve_attempts`）
- `top_match_score` / `top_normalized_score`：最终通过时候选中的最佳指标
- `source_count`：通过时保留的 chunk 数量

这些指标可以回答面试官的“检索做得好不好”：

- 好：top_match_score 高、irrelevant_ratio 低、retrieve_attempt 少
- 差：top_match_score 低、low_grounding_count 上升、fallback/no_retrieval_hit 增多

## 4. 离线/可解释评估指标（RAG 生成对齐与证据约束）

RAG 生成阶段的核心质量锚点是 `grounding_score` 与证据约束。

### 4.1 生成对齐指标（`grounding_score`）

在 `src/kb/engine.py` 中，最终生成答案会被视为一个“query”，与检索证据做匹配：

- 对每个证据 chunk 以及“整体拼接上下文”，计算 `evaluate_retrieval(answer, evidence_text)`
- 取最大的 `normalized_score` 作为 `grounding_score`

可用于落地的阈值：

- `rag_answer_grounding_min_score`：是否通过的底线（默认在代码里约 `0.18` 量级）

### 4.2 证据约束指标（`has_evidence_citations`）

答案必须显式带证据编号：

- 若包含 `无法确认` 字样：允许通过
- 否则必须匹配形如 `[证据N]` 的证据编号

对应 trace 字段：

- `has_evidence_citations`（bool）

### 4.3 重生成指标（`regenerate_count` 与 final_status）

系统最多重生成 `rag_answer_max_regenerate_times` 次（实现里是最多 3 次级别）。
当 `grounding_score < min_score` 或缺少证据时会触发重试。

对应 trace：

- `regenerate_count`：重生成次数（大于 0 说明首次生成不达标）
- `final_status`：
  - `rag_grounded`：首次就通过（尝试次数为 0 且满足 grounding 与证据）
  - `rag_regenerated`：通过发生在重生成后
  - `rag_fallback_unconfirmed`：重生成后仍无法达标（低 grounding 或缺少证据）
  - `rag_no_hit` / `rag_no_context`：检索没命中或上下文为空

这组指标的面试回答可以这样说：
> 我们不是只看“生成出来了”，而是用 `grounding_score + 证据编号` 做硬门控；门控失败就重生成或兜底，因此可以把质量问题拆成“检索问题”与“生成对齐问题”。

## 5. 高频 QA 离线评估指标（阈值标定用 Precision/Recall/FPR）

高频 QA 属于快路径：一旦误命中模板问答，错答成本通常更高，因此阈值标定强调 Precision。

离线标定目标（来自 `docs/问答阈值校准.md`）：

- `qa_semantic_min_score`
- `qa_semantic_min_query_coverage`

标定阶段输出：

- precision（命中正确率）
- recall（拒绝了多少仍能命中的正样本）
- FPR（误命中率：把负样本错当正样本的比例）

标注集与 sweep 脚本示例：

- 标注集字段包括 `query / gold_question / label`
- 通过 `scripts/qa_threshold_sweep.py` 做阈值扫描

门控条件维度（除了主维度 score 与 coverage 外，还有额外防线）：

- `qa_semantic_min_margin`
- `qa_semantic_max_irrelevant_ratio`
- `qa_semantic_min_ngram_overlap_count`
- `qa_semantic_min_query_chars`

落到 trace / observation 的字段（来自 `KnowledgeEngine.query()` 中对 qa 命中的追踪）：

- `qa_match_type`
- `qa_match_score`
- `qa_query_coverage`
- `qa_top2_score`
- `qa_margin`
- `qa_irrelevant_ratio`
- `qa_ngram_overlap_cnt`

## 6. 评估如何用起来（闭环流程，面试官最关心“怎么改进”）

下面给一个从“提出问题”到“指标驱动改进”的闭环，确保你能在面试里回答得很落地。

### 6.1 线上问题定位

1. 先看总览指标：success/avg_latency/low_grounding/fallback/regenerated
2. 再看分桶：按 `route` 与 `llm_endpoint_name`、`response_mode` 观察变化
3. 最后落到差评案例：用 `GET /qa/analytics` 的 `bad_cases` 抽样人工复盘

### 6.2 决策：是“检索不足”还是“生成对齐不足”

- 若 `retrieve_attempt` 高 + `top_match_score` 低：优先怀疑检索侧（向量/ BM25 融合、阈值、top_k、重排参数）
- 若 `grounding_score` 低 + 缺证据多：优先怀疑生成对齐侧（prompt 约束、重生成次数、证据编号规则）
- 若 `low_grounding_count` 与 `fallback_count` 联动上升：说明门控策略或证据覆盖率不足，需要配合 trace 看证据命中类型

### 6.3 离线标定（只在高风险阈值上做）

针对高频 QA：

1. 用标注集做 precision/recall/FPR 的 sweep
2. 固化推荐阈值到配置（`config/settings.py`）
3. 线上观察 `cache_hit_count/qa_hit/fallback_count/low_grounding_count` 是否下降

针对 RAG 检索评估：

1. 以 `evaluate_retrieval()` 输出分数作为特征
2. 用线上 trace 抽样案例对比不同检索参数对 `top_normalized_score` 与 `grounding_score` 的影响

## 7. 面试可直接背的回答版本（30 秒）

我们对智能体的评估分三层：效果、可靠性、性能成本。线上我们把每条请求按 `observation_id` 落库到 `qa_observation` 与 `qa_rag_trace`，聚合统计 `success_rate、avg_latency_ms、cache_hit_count、fallback_count、low_grounding_count、regenerate_count`，并通过 `GET /qa/analytics` 拉差评案例。效果质量上，RAG 的关键指标是 `top_match_score`（检索是否命中相关证据）和 `grounding_score`（答案与证据对齐度），同时用硬门控要求答案带 `[证据N]`，门控失败会重生成或兜底，最终落到 `final_status`。离线方面，我们的检索评估 `evaluate_retrieval()` 是纯规则可复算的，且高频 QA 的阈值用 precision/recall/FPR 做可复现 sweep，从而控制误命中风险。
